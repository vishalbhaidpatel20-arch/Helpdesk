# Helpdesk

AI-powered ticket management system. Support emails become tickets; AI (Google Gemini) classifies them, summarizes them, and suggests replies drawn from a knowledge base. Agents work tickets from a dashboard, and admins manage agents.

Reference docs in the repo root:
- `project-scope.md` — problem, solution, feature list
- `tech-stack.md` — chosen technologies
- `implementation-plan.md` — phased build plan (setup → auth → ...)

## Structure

Bun workspaces monorepo (`core`, `client`, `server`).

- `core/` — `@helpdesk/core`, shared TypeScript package (source-only, no build step) imported by both `client` and `server`. Currently holds zod schemas in `core/src/schemas/`, exported from `core/src/index.ts`.

- `client/` — React 19 + TypeScript, Vite, Tailwind CSS v4, shadcn/ui (radix-nova), React Router
  - `client/src/components/ui/` shadcn components; `@/` aliases `client/src/`
- `server/` — Express 5 + TypeScript running on Bun, Prisma 7 with PostgreSQL (`@prisma/adapter-pg`)
  - `server/prisma/` schema and migrations; `server/generated/` is Prisma client output (do not edit)

## Commands

Run from the repo root unless noted.

- `bun install` — install all workspace dependencies
- `bun run dev:server` / `bun run dev:client` — start each dev server
- `bun run dev` — start both
- `bun run --cwd client build` — typecheck and build the client
- `bun run --cwd client lint` — lint client with oxlint
- `bun run --cwd server typecheck` — typecheck the server
- `bun run --cwd server db:migrate` — create/apply a Prisma migration
- `bun run --cwd server db:generate` — regenerate the Prisma client
- `bun run --cwd client test` — run client component tests (Vitest + React Testing Library, jsdom; files are `*.test.tsx` next to the code, setup in `client/src/test/setup.ts`; mock `@/lib/api` rather than the network)
- `bun run --cwd client test:watch` — Vitest watch mode: reruns affected component tests on every save, for writing tests
- `bun run --cwd server test` — run server unit tests (`bun test`, files are `*.test.ts` next to the code; mock external services such as the AI SDK, never call them)
- `bun run test:e2e` — run the Playwright e2e tests (`test:e2e:ui` for the UI runner)

## Conventions

- Use Bun as the package manager and runtime (not npm/yarn/pnpm).
- TypeScript everywhere; ES modules (`"type": "module"`).
- Authentication uses database-backed sessions, not JWTs.
- AI features (classification, summaries, polishing, auto-resolve) call Google Gemini through the Vercel AI SDK (`generateWithFallback` tries `gemini-3.8-flash`, then falls back to smaller models when overloaded); the key is `GOOGLE_GENERATIVE_AI_API_KEY`.
- Ticket statuses: New, Processing (system-only, see "AI processing"), Open, Resolved, Closed. Categories: General Question, Technical Question, Refund Request.
- Client styling is Tailwind utilities and shadcn/ui components with the default theme. No custom CSS: `client/src/index.css` holds only the Tailwind/shadcn theme output.
- After `bunx shadcn add`, check new files in `components/ui/` for `from "cn"` (an unrelated npm package) and change it to `@/lib/utils`. Don't add `baseUrl` to the tsconfigs (deprecated in TS 6); the `@/*` alias uses `paths` only.
- Client data fetching: use axios, never `fetch`, through the shared instance in `client/src/lib/api.ts` (`baseURL: '/api'`). Wrap calls in TanStack Query (`@tanstack/react-query`) with `useQuery` / `useMutation`, usually in a hook under `client/src/hooks/` (see `useUsers`), and pass the query's `signal` to axios. Don't fetch in `useEffect` with manual loading/error state. Better Auth calls go through `authClient`, not axios. The query cache is cleared on sign-out.
- Data tables use TanStack Table (`@tanstack/react-table`, v9 API, not v8). Sorting, filtering and pagination of server data are done by the server (`manualSorting`, etc.), never client-side; keep the sort/filter/page state in the URL (see `useTicketParams`).
- Client forms use react-hook-form with a zod schema via `zodResolver` (`@hookform/resolvers/zod`), including the user form (`client/src/components/UserForm.tsx`, used to create a user in `CreateUserDialog` and to edit one in `EditUserDialog`; editing leaves the password unchanged when it is blank). Don't hand-roll form state or validation.
- Define every zod schema used for validation (request bodies, forms) once in `core/src/schemas/` and export it from `core/src/index.ts`. Import it from `@helpdesk/core` in both client and server; never redefine or copy a schema in either one. Shared constants like password length limits live there too. Example: `createUserSchema` is used by `UserForm` (with `updateUserSchema` for edits) (via `zodResolver`) and by `POST /api/users`. Client forms use `zodResolver` with react-hook-form, and server routes validate request bodies with `parseBody(schema, req, res)` and query strings with `parseQuery(schema, req, res)`, both from `server/src/lib/parseBody.ts` (they send the 400 with the first issue's message and return undefined) rather than hand-written checks.
- Don't use TypeScript `enum` in code the client compiles (including `core`): the client tsconfig has `erasableSyntaxOnly`, which rejects enums. Use a union type when only the type is needed, and an `as const` object plus a derived type when runtime access is needed (e.g. `TicketStatus` in `core/src/schemas/ticket.ts`, `Role` in `client/src/lib/roles.ts`): `export const X = { A: 'A' } as const` and `export type X = (typeof X)[keyof typeof X]`. Prisma enums (generated, server only) are the exception; mirror them this way for the client.
- Express 5 forwards rejected promises from async route handlers to the error handler automatically, so don't wrap handlers in try/catch or write async wrappers; let errors propagate to the terminal handler in `server/src/index.ts` (use try/catch only to handle a specific expected error).
- Secrets live in `.env` (loaded with dotenv); never commit them.

## Users

- Users are soft-deleted: `User.deletedAt` is set instead of removing the row. Always filter `deletedAt: null` when listing or looking up users for the UI; `DELETE /api/users/:id` also revokes the user's sessions and unassigns their tickets, and the Better Auth `session.create.before` hook in `server/src/auth.ts` blocks sign-in for deleted users. A deleted user's email stays reserved (the unique constraint still applies).
- Admins cannot be deleted (the endpoint returns 403 and the UI hides the delete button), which also prevents self-deletion. Deleting asks for confirmation in `DeleteUserDialog`.

## Tickets and inbound email

- `Ticket` model (`server/prisma/schema.prisma`): numeric autoincrement `id`, `subject`, `body`, required `senderName` / `senderEmail`, unique optional `messageId`, `status` (default `NEW`) and optional `category` (no default; null until classified). `TicketStatus` / `TicketCategory` and the `Ticket` list type are defined in `core/src/schemas/ticket.ts`; use them in the client instead of string literals.
- Support emails arrive at `POST /api/webhooks/inbound-email` (`server/src/routes/webhooks.ts`). No email provider is wired up yet: the endpoint takes JSON validated by `inboundEmailSchema` (`senderName`, `senderEmail`, `subject`, `text`, optional `messageId`) and is authenticated by the `x-webhook-secret` header matching the `INBOUND_EMAIL_SECRET` env var (401 if wrong, 503 if unset; add it to `server/.env` and `server/.env.test`). A repeated `messageId` returns the existing ticket (200) instead of creating a duplicate (201 when new). Future SendGrid/Mailgun adapters should map their payloads onto this schema.
- Email can also arrive over SMTP (`server/src/lib/smtpServer.ts`, started from `server/src/index.ts`): `smtp-server` receives the message, `simpleParser` (`mailparser`) turns it into a `ParsedEmail` (from, to, cc, subject, date, messageId, text, html, attachments), and `handleIncomingEmail` (`handleIncomingEmail.ts`) validates it with `inboundEmailSchema` and calls `createTicketFromEmail`, the same function the webhook uses (so duplicate `messageId`s, AI processing and assignment behave identically). It is off unless `SMTP_DOMAIN` is set; only recipients at that domain are accepted (550 otherwise, so it is never an open relay) and AUTH is disabled. Optional env: `SMTP_PORT` (default 2525), `SMTP_HOST` (default 0.0.0.0), `SMTP_MAX_MESSAGE_BYTES` (default 10 MiB, 552 above it). Replies: 550 for mail that can never be a ticket, 451 for temporary failures so the sender retries. Only the plain text body is stored; the HTML body and attachments are parsed but not saved. `SMTP_PASSWORD` in `server/.env` is a Gmail app password.
- Agent replies are emailed to the customer (`server/src/lib/sendEmail.ts`, `nodemailer` over SMTP; IMAP can only read mail). `POST /api/tickets/:id/replies` sends first and saves the `Reply` only if the mail server accepted it (502 with a message otherwise, so a retry never leaves a duplicate). The email is "Re: <subject>" with `In-Reply-To`/`References` set to the ticket's `messageId` so mail clients thread it. Sending is on when `MAIL_USER` (or `IMAP_USER`) is set; the password is `MAIL_PASSWORD`, falling back to `SMTP_PASSWORD` (spaces removed). Optional: `MAIL_HOST` (default `smtp.gmail.com`), `MAIL_PORT` (default 465 = TLS, otherwise STARTTLS), `MAIL_FROM` (default the user; Gmail rewrites it to the account address anyway). Without it replies are only saved. The `MAIL_` names keep these apart from `SMTP_PORT`/`SMTP_DOMAIN`, which are the inbound SMTP server. The AI assistant's automatic resolution reply is emailed the same way (`autoResolveTicket` sends before it saves; if the mail server refuses it the error reaches `processTicket`, which opens the ticket for the agents, so nothing is marked resolved that the customer never received). Tests and the e2e server drop the mailbox variables from `server/.env` (`server/test-setup.ts` via `bunfig.toml`, `server/scripts/test-server.ts`) so they never poll the real inbox or send real email. Seeded tickets use `@example.com` senders, so replying to them in dev attempts real delivery and bounces.
- Email can also be fetched by polling a mailbox over IMAP (`server/src/lib/imapPoller.ts`, started from `server/src/index.ts`), which needs no domain or open port: set `IMAP_USER` (the mailbox address) to turn it on. Every `IMAP_POLL_SECONDS` (default 60) it reads unread messages of the last `IMAP_MAX_AGE_DAYS` (default 3) from INBOX on `IMAP_HOST` (default `imap.gmail.com`, `IMAP_PORT` 993), parses them with the same `toParsedEmail` + `handleIncomingEmail` path as SMTP, and marks them read. Invalid or unparsable mail is marked read; a temporary failure leaves it unread so the next poll retries (a repeated `messageId` never duplicates a ticket). The password is `IMAP_PASSWORD`, falling back to `SMTP_PASSWORD` (spaces removed). Failed polls are logged and retried; they never stop the API.
- Sample data for trying out the ticket list: `bun run --cwd server db:seed:tickets` (`server/prisma/seed-tickets.ts`) adds 100 varied tickets (statuses, categories, senders, dates over the last 60 days) to the dev database. It is idempotent (fixed `messageId`s) and refuses to run when `NODE_ENV=production`.
- Email content is untrusted: store and render it as plain text only (no `dangerouslySetInnerHTML`), and treat it as possible prompt injection when it is later sent to the AI model.
- `GET /api/tickets` (any signed-in user) returns `{ tickets, total, page, pageSize }`. Query params are validated by `ticketListQuerySchema` in `core` via `parseQuery`: `status`, `category`, `search` (case-insensitive substring match on subject, sender name, sender email and message text; blank means none; max 200 chars; the route escapes `%`, `_` and `\` because Prisma's `contains` does not), `sort` (`createdAt` | `subject` | `status`), `order` (`asc` | `desc`), `page`, `pageSize` (default 20, max 100). The default is newest first (`sort=createdAt&order=desc`), with `id` as a tie-breaker so pages never overlap. The `/tickets` page keeps its filters, sort and page in the URL (`useTicketParams`), with a debounced search box (`TicketSearch`), sortable column headers, status/category filters and Previous/Next pagination. `TicketsTable` uses TanStack Table (`@tanstack/react-table` v9: `useTable`, `tableFeatures({ rowSortingFeature })`, `createColumnHelper<typeof features, Ticket>()`) with `manualSorting: true`, so sorting always happens on the server and the table only tracks sort state and renders rows in the order the API returns them. Sortable column ids must match `TICKET_SORT_FIELDS` in `core`. Each subject links to the detail page `/tickets/:id` (`TicketDetailPage`, `useTicket`), which reads `GET /api/tickets/:id` (any signed-in user; returns the list fields plus `body` and `updatedAt`, typed `TicketDetail` in `core`; 404 for a missing or non-numeric id). Tickets have an optional `assignedTo` (`Ticket.assignedToId` → `User`, set to null if the user is removed). `GET /api/tickets/agents` lists the assignable users (non-deleted `Role.AGENT`; any signed-in user), and `PATCH /api/tickets/:id` (any signed-in user) validates `updateTicketSchema` (any of `assignedToId`, `status`, `category`, at least one; `null` unassigns or clears the category) and changes only the fields sent (400 for an unknown, deleted or non-agent assignee, 404 for a missing ticket). The detail page edits all three with selects (`TicketAssignee` and `useUpdateTicket`). Replies and threading are not built yet. The reply form has a Polish button: `POST /api/tickets/:id/replies/polish` (body validated by `polishReplySchema`) returns `{ body }`, the draft improved by `gemini-3.8-flash` through the Vercel AI SDK (`server/src/lib/polishReply.ts`, key in `GOOGLE_GENERATIVE_AI_API_KEY`; 503 if unset). The server adds the greeting (customer first name) and a signature (agent name and GitHub link). Nothing is saved; the client puts the result back in the textarea (`usePolishReply`). The detail page also has a Summarize button (sparkles icon, `TicketSummary`) under the email: `POST /api/tickets/:id/summary` returns `{ summary }` (`TicketSummary` type in `core`), an AI summary of the email and all replies made by `server/src/lib/summarizeTicket.ts` on every click (never cached or saved; 503 if the key is unset, 502 if the provider fails).

## AI processing of new tickets

- The inbound-email webhook creates the ticket as `NEW` and queues a `process-ticket` job with pg-boss (`server/src/lib/queue.ts`; its tables live in the database's own `pgboss` schema; no retries; the worker starts in `server/src/index.ts`). Without `GOOGLE_GENERATIVE_AI_API_KEY` the ticket is created `OPEN` and nothing is queued (so e2e tests are unaffected); if queueing fails it is set `OPEN`.
- `processTicket` (`server/src/lib/processTicket.ts`) only orchestrates two independent components: classification (`classifyAndSaveTicket` in `classifyTicket.ts`, fills `category` only while it is null) and auto-resolve (`autoResolveTicket` in `autoResolveTicket.ts`, which answers from `server/knowledge-base.md` via `knowledgeBase.ts` and `resolveTicket.ts`). Each has its own tests and neither imports the other. It sets `PROCESSING` first. The model returns JSON `{ canResolve, confidence, reply }`; below `MIN_CONFIDENCE`, unparsable output, a missing KB file or the KB's escalation rules (legal threats, chargebacks, refunds after 30 days, security) mean no resolution. Resolved: status `RESOLVED` plus a `Reply` with `authorId: null` (shown as "AI Assistant"; emailed to the customer when sending is configured, see above). Otherwise `OPEN`. Statuses change only while still `NEW`/`PROCESSING`, so an agent's edit is never overwritten, and any failure (e.g. `generateText` throws) opens the ticket immediately instead of retrying, so nothing stays hidden.
- `GET /api/tickets` excludes `NEW`/`PROCESSING` tickets (and the list's status filter and `PATCH` accept only `AGENT_TICKET_STATUSES` from `core`); `/tickets/:id` still opens them.
- AI agent: `bun run --cwd server db:seed:ai` (`server/prisma/seed-ai-agent.ts`, idempotent) creates the agent "AI" (`ai@helpdesk.local`, `Role.AGENT`, no credential account so nobody can sign in as it; `server/src/lib/aiAgent.ts`). While it exists, the webhook assigns every new ticket to it; a ticket it resolves stays assigned to it, and `openTicket` (in `autoResolveTicket.ts`) unassigns it when the ticket could not be resolved (only if still assigned to the AI).
- `Ticket.resolvedAt` is set when a ticket becomes RESOLVED/CLOSED (by the AI or `PATCH`) and cleared when it is set back to OPEN. Dashboard (`/dashboard`, `DashboardPage`, `useTicketStats`) reads `GET /api/stats` (any signed-in user; `TicketStats` in `core`). The numbers are computed by the Postgres function `ticket_stats(days)` (created in the `ticket_stats_function` migration; the route in `server/src/routes/stats.ts` only calls it and returns its JSON), so change the stats by adding a new migration that `CREATE OR REPLACE`s the function, not by editing the route: total tickets, OPEN tickets, tickets resolved by AI (RESOLVED/CLOSED with a reply that has no author), that as a % of all tickets, and the average `resolvedAt - createdAt`. The five numbers sit in one row (on wide screens), followed by `TicketsPerDayChart`, a plain-SVG bar chart of tickets created per UTC day over the last 30 days (`ticketsPerDay` in the stats response, zero-filled by the server; hover readout and a screen-reader table included).
- Assignee filter: `GET /api/tickets` and `GET /api/stats` take `assignee=me|all` (`TICKET_ASSIGNEE_FILTERS` in `core`; `me` = assigned to the caller, missing = all). The client defaults to `me` for agents and `all` for admins (`useDefaultAssignee`), with a "Show" select on `/tickets` and `/dashboard` and the choice kept in the URL. It is a default view, not access control. `ticket_stats(days, assignee_id)` takes the assignee (see the `ticket_stats_assignee` migration).
- `bun run --cwd server db:classify:tickets` queues jobs for tickets that still have no category (it does not change statuses of tickets already past `NEW`).

## Error reporting (Sentry)

- Server: `server/src/instrument.ts` (`@sentry/bun`) is imported first in `server/src/app.ts` and `index.ts`; the terminal error handler in `app.ts` calls `Sentry.captureException` for server faults (not 4xx errors such as malformed JSON; Sentry's own `setupExpressErrorHandler` is deprecated and its replacement `expressIntegration` is not enabled by default on Bun), and the SDK is flushed on shutdown. Handled failures go through `reportError(context, err)` (`server/src/lib/reportError.ts`: `console.error` plus `Sentry.captureException`) instead of a bare `console.error`: failed polls, ticket processing, pg-boss, SMTP, reply emails, AI polish/summary. Client: `client/src/instrument.ts` (`@sentry/react`) is imported first in `main.tsx`, and `createRoot` uses `Sentry.reactErrorHandler()` for React 19's error hooks.
- Off unless `SENTRY_DSN` (server, in `server/.env`) or `VITE_SENTRY_DSN` (client, in `client/.env`, see `client/.env.example`) is set; `SENTRY_ENVIRONMENT` is optional. Unit tests and the e2e server drop `SENTRY_DSN`.
- Privacy: tickets and emails are customers' personal data and requests carry session cookies and the webhook secret. SDK v11 collects bodies, cookies, headers, query strings and local variables by default, so `dataCollection` turns them all off in both `instrument.ts` files, and on the server `scrubEvent` (`server/src/lib/scrubEvent.ts`) also strips everything but the request method and path. Don't add email content or addresses to `extra`/tags.

## Deployment (Vercel)

- One Vercel project serves the built client (`client/dist`, CDN) and the API: `server/src/app.ts` exports the Express app (no listening, no background work), `api/index.ts` re-exports it as the Vercel Function (Bun runtime, `bunVersion` in `vercel.json`), and `vercel.json` rewrites `/api/*` to it and everything else to `index.html`. See `DEPLOYMENT.md` for the steps. Env template: `server/.env.example`.
- `server/src/index.ts` is the long-lived entry for local development (`bun run dev:server`) and for container hosting (`Dockerfile`, optional): it imports the app, listens, serves `client/dist` in production, starts the pg-boss worker, the SMTP server and the IMAP poller. None of that runs on Vercel.
- Vercel differences (`process.env.VERCEL` is set there): `enqueueProcessTicket` runs `processTicket` with `waitUntil` from `@vercel/functions` instead of sending a pg-boss job; the IMAP poller is replaced by `GET /api/cron/poll-inbox` (`server/src/routes/cron.ts`, authenticated by `Authorization: Bearer $CRON_SECRET`, 503 if unset), called by the Vercel Cron job in `vercel.json` (daily, because Hobby accounts reject more frequent schedules; use `*/5 * * * *` on Pro or an external scheduler); the Prisma pool is limited to one connection per instance, so `DATABASE_URL` must be the provider's pooled string; `server/knowledge-base.md` and `server/generated` are bundled with the function by `includeFiles`. Leave `SMTP_DOMAIN` unset (no raw SMTP on Vercel).
- The build command in `vercel.json` runs `prisma generate`, `prisma migrate deploy` (so `DATABASE_URL` is needed at build time) and the client build. `VITE_*` values are baked in at build time. `BETTER_AUTH_URL` and `CLIENT_URL` are the same public https URL (production domain; previews need their own values).

## Authentication

Better Auth with email/password and database-backed sessions (Prisma adapter, PostgreSQL).

- Server config: `server/src/auth.ts`. The handler is mounted at `/api/auth/*splat` in `server/src/app.ts`, **before** `express.json()` (which would consume the request body). Keep that order.
- Public sign-up is disabled (`disableSignUp: true`). Users are created only by an admin; there is no self-registration.
- Roles: `Role` enum `ADMIN` | `AGENT` on `User.role`. Never hardcode role strings (`'ADMIN'`, `'AGENT'`), in app code or tests: on the server import `Role` from `server/generated/enums`; everywhere in the client (components, hooks, tests, mock data) use `Role` from `@/lib/roles` for both comparisons and the `Role` type (it mirrors the Prisma enum, since the client can't import server code, so update it when the enum changes). New users created from the Users page get `Role.AGENT`. It defaults to `AGENT` and is not settable from client input (`input: false`).
- Soft delete of users is described under "Users" above; new user queries must filter `deletedAt: null`, and the `session.create.before` hook in `server/src/auth.ts` blocks sign-in for deleted users. The user list and edit/delete treat deleted users as not found.
- First admin comes from the seed script: `bun run --cwd server db:seed`, which reads `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` from `.env`. It is idempotent and creates users through Better Auth's internal adapter (`ctx.internalAdapter`) because sign-up is disabled.
- Env vars: `CLIENT_URL` (required; the server throws on startup without it and uses it as the trusted origin), plus Better Auth's own secret and base URL variables. `server/src/index.ts` currently hardcodes CORS to `http://localhost:5173`.
- Client: `client/src/lib/auth-client.ts` creates the client with no `baseURL`; requests go to the current origin and Vite proxies `/api` to the server on port 3000.
- Client role access: `authClient` uses `inferAdditionalFields`, so `session.user.role` is typed. Admin-only pages go inside `<AdminRoute />` (`client/src/components/AdminRoute.tsx`), which redirects non-admins to `/`; the nav link to `/users` in `Layout.tsx` shows only for admins. Current admin-only page: `/users`.
- Route protection: `client/src/components/ProtectedRoute.tsx` wraps authenticated pages and redirects to `/login` without a session; `Layout.tsx` (inside it) renders the nav bar. `LoginPage` redirects to `/` when already signed in. All use `authClient.useSession()`. These checks are UI-only; protect server routes by checking the session with `auth.api.getSession`.

## Component tests

Client component tests use Vitest + React Testing Library (jsdom). They are separate from the Playwright e2e tests below.

**Testing policy: rely mostly on component tests.** They are fast, run without a database or servers, and are the default for any UI behaviour: rendering states, forms and validation, dialogs, sorting/filter/pagination controls, URL state (render inside a `MemoryRouter` and assert on the location), permission variants. Write an e2e test only when it is necessary, meaning the behaviour needs the real server, database, browser or auth session (see the end-to-end section). If a behaviour can be checked with a mocked `@/lib/api`, it belongs in a component test, not in e2e.

- **Run:** `bun run --cwd client test` for a single run; `bun run --cwd client test:watch` while writing. Run the tests, plus `bun run --cwd client build` (it typechecks the test files) and `lint`, after changing a component or its test, and report the real results.
- **Where:** `*.test.tsx` next to the code under test (e.g. `client/src/pages/UsersPage.test.tsx`). Config is the `test` block in `client/vite.config.ts`; `client/src/test/setup.ts` loads the jest-dom matchers and cleanup. Vitest globals are off: import `describe`, `it`, `expect`, `vi` from `vitest`.
- **Render helper:** use `renderWithQuery(ui)` from `@/test/renderWithQuery` for anything using TanStack Query. It creates a fresh `QueryClient` per call with retries off. Add other shared helpers to `client/src/test/`.
- **Mocking:** mock `@/lib/api` with `vi.mock('@/lib/api', () => ({ api: { get: vi.fn() } }))` and set results per test (`mockResolvedValue`, `mockRejectedValue`, or a never-resolving promise for loading). Reset mocks in `beforeEach`. Build HTTP errors with `new AxiosError(..., { status } as AxiosResponse)` so `axios.isAxiosError` works. Never hit the network or the database. Mock `authClient` for components that use the session.
- **Queries:** use accessible queries (`getByRole`, `getByLabelText`, `getByText`), scoped with `within` for rows. Use `findBy*` or `waitFor` for async results, never fixed timeouts. Use `data-slot="skeleton"` to detect skeletons. Don't assert on Tailwind classes or implementation details.
- **Coverage per component:** loading, success, empty, and error states, plus role or permission variants. Compute expected values (e.g. dates) with the same function as the component instead of hardcoding locale output.
- **Check the tests can fail:** temporarily break the component and confirm the relevant test fails, then restore it.
- Don't test third-party UI (shadcn/Radix internals) or the server here. Server behaviour that can't be mocked away belongs in the e2e tests (see the policy above).

## End-to-end tests

Playwright tests live in `e2e/`; config is `playwright.config.ts` at the repo root.

- **Use e2e tests only when necessary.** Prefer component tests (see the testing policy above). Add or keep an e2e test only for what a component test cannot prove: the real API contract and server logic (e.g. the inbound-email webhook, auth and authorization, soft-delete blocking sign-in), data that must round-trip through the real database (e.g. real ordering and paging), and behaviour that depends on the browser session or cookies. Keep each flow to a few happy paths. Don't use e2e for UI-only behaviour such as sort/filter toggles, validation messages, dialog open/close, or URL state. Before writing an e2e test, check whether a component test could cover it, and when a feature's UI behaviour is already covered by component tests, don't duplicate it in e2e.

- **Use the `e2e-test-writer` subagent (`.claude/agents/e2e-test-writer.md`) for writing, updating, or fixing e2e tests.** Do not write Playwright tests directly in the main session.
- Isolated test environment: Playwright starts the API on port 3001 and the client on port 5174 (never the dev ports 3000/5173). `server/scripts/test-server.ts` loads `server/.env.test` (gitignored; copy from `.env.test.example`), then resets and seeds the separate `helpdesk_test` database before each run. It refuses any database name not ending in `_test`.
- The seed creates only the admin (`SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` from `.env.test`). Tests that need other users, such as an agent, must create them themselves, since public sign-up is disabled.
- Rate limiting is production-only, so tests can sign in repeatedly.
- `prisma migrate reset` is blocked for AI agents by Prisma's safeguard. If it blocks a run, stop and ask the user to run it; never set `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` without the user's explicit consent.

## Documentation lookup (Context7)

The `context7` MCP server is configured for this project. Always use it to fetch current documentation instead of relying on memory when working with any library, framework, SDK, or API. This matters here because the stack uses recent major versions (React 19, React Router 8, Vite 8, Tailwind 4, Express 5, Prisma 7, TypeScript 6) whose APIs differ from older training data.

1. Call `resolve-library-id` with the library name to get its Context7 ID.
2. Call `query-docs` with that ID and a specific question.

Use it for API syntax, configuration, setup, version migration, and library-specific debugging (e.g. Prisma driver adapters, React Router data APIs, Tailwind v4 config, Express 5 routing, Anthropic SDK usage). Skip it for general programming concepts or business-logic questions.
